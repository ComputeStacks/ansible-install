# ssh_trust

Installs the controller's root and application SSH keys into root's
`authorized_keys` on every node and registry host — control-plane rows #4 and
#19 (docs/contracts.md): the controller manages tenant registries over SSH
(`DockerSSH`) and every node over SSH (volumes, haproxy cert deploy, LB
reload) as root, keyed off two pubkeys generated on the controller.

| Runs in | Play | Hosts |
| --- | --- | --- |
| `site.yml` | "SSH trust" | `controller:nodes:registry` |
| `add-region.yml` | "SSH trust for the new node" | `controller:nodes` |
| `upgrade-docker.yml`, `unseal.yml` | not run | — |

**Attach mode:** keys are added to the new node only; on an `existing_env`
controller the role only reads the two pubkeys and skips its `/root/.ssh/config`
render. **Requires:** `common` (the controller's root keypair) and, on a
greenfield controller, `controller` (the application keypair).

## What it does

1. Slurps the controller's root pubkey (`/root/.ssh/id_ed25519.pub`,
   generated by the `common` role) and its app pubkey
   (`ssh_trust_app_pubkey_path`, see below). A missing app pubkey is a
   **hard failure** in both modes: `site.yml` runs the controller role — the
   role that creates the key — before this play, and a live controller of either
   generation always has one. Installing only the root key would leave the
   controller unable to manage volumes, deploy haproxy certificates or
   reload LBs on the host, and nothing would surface until production
   traffic hit it.
2. Installs both keys as additive `authorized_key` entries into root's
   authorized_keys on every host in `groups['nodes']` **and**
   `groups['registry']`.
3. On the controller, renders `/root/.ssh/config` (whole-file) with a `Host`
   block per node, using inventory vars only (`hostname`, `primary_ip`) —
   **skipped entirely** when the controller is flagged `existing_env: true`
   (attach mode never renders a shared/controller file whole;
   docs/contracts.md rule 9).

## Variables

| Variable | Default | Purpose |
| --- | --- | --- |
| `ssh_trust_app_pubkey_path` | `""` (detect) | Forces where the controller's **application** ed25519 pubkey lives, on the controller host. Empty means probe `ssh_trust_app_pubkey_candidates` and take the first that exists. |
| `ssh_trust_app_pubkey_candidates` | v2 `/etc/computestacks/.ssh/`, then v1 `ssh_keys_directory` | Probed in order, so a controller migrated from v1 resolves to the key its running application actually uses. |

Probing on the controller, rather than choosing a path from the controller's
`existing_env` flag, is deliberate: `existing_env` means "not mine to rebuild,
partial inventory", not "built by v1", so an environment this repository built
can be attached to as well. The candidates, in order:

* `/etc/computestacks/.ssh/id_ed25519.pub` — the v2 location (`roles/controller`).
  Checked first: a controller migrated from v1 can still carry the old
  directory, and the key its running application uses is this one.
* `/var/lib/computestacks/sshkeys/id_ed25519.pub` — v1's `ssh_keys_directory`
  (v1 `roles/controller/defaults/main.yml`), where an existing v1 controller
  keeps it.

Set `ssh_trust_app_pubkey_path` directly if a controller keeps its key
elsewhere.

Consumed, not owned: `groups['controller']`, `groups['nodes']`,
`groups['registry']`, `hostname`/`primary_ip` (node inventory vars),
`existing_env`, `cs_ports.ssh` (`playbooks/group_vars/all/ports.yml`).

## Scope

The rendered `/root/.ssh/config` has a `Host` block per node only, and keys go
to `groups['nodes']` and `groups['registry']` only — the two groups the
controller manages over SSH. Checking that the controller can actually connect
is `roles/validate`'s `ssh` check, not this role's.
